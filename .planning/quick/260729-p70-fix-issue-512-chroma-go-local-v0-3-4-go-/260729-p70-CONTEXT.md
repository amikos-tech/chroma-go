<confirmed_root_cause>
## Root Cause — CONFIRMED, not assumed

The `v0.3.4` tag in `amikos-tech/chroma-go-local` was re-cut after `sum.golang.org`
notarized the original content. Confirmed by direct experiment:

```
GOPROXY=direct GOSUMDB=off go mod download -json github.com/amikos-tech/chroma-go-local@v0.3.4
  "Sum":      "h1:7yFDZuu9qRtRd/w6sZZqWwk/j1dcw3+Ly8MBuf3H+KI="   <- live tag content
  "GoModSum": "h1:U37BtxfJldfcpiya6nelgy+SdMesYOVub9kcnRknTrk="
  "Origin":   { VCS: git, Hash: ad3a5aa68f0434670bb8cc39811e69930f40ea70, Ref: refs/tags/v0.3.4 }
```

The live tag content hashes to exactly the value CI downloaded (`7yFDZuu9...`), which
disagrees with the immutable `sum.golang.org` record (`NUCaw0R...`, which matches this
repo's `go.sum:60`).

Supporting evidence:

1. **Only the source tree changed, not `go.mod`.** `GoModSum` (`U37BtxfJ...`) matches the
   sumdb entry exactly; only the tree hash differs. The re-cut altered files without
   touching dependency declarations.
2. **`v0.3.3` is intact.** Direct fetch yields `h1:jVsOSC0M85d/e2xSTsF36B5NUmY7Uu2jkl2rG+hTt74=`,
   identical to its sumdb entry. The problem is isolated to the `v0.3.4` tag — not systemic
   proxy corruption, not tampering.
3. **`proxy.golang.org` 404s `v0.3.4` entirely.** `.info`, `.mod`, `.zip`, and `@latest` all
   return HTTP 404 while `@v/list` still lists the version; `v0.3.3` returns 200. Because the
   default `GOPROXY` is `https://proxy.golang.org,direct`, a 404 falls through to a direct
   GitHub fetch, which returns the re-cut content, which then fails the `go.sum` check. This
   is the complete failure mechanism.
4. **Tag metadata looks superficially clean** — tagger date `2026-03-19T10:02:03Z`, target
   commit `ad3a5aa` committed `2026-03-19T10:00:15Z`. The re-tag preserved plausible timing,
   which is why the GitHub API alone does not reveal it.

**Severity is higher than the issue states.** `sum.golang.org` is append-only; the `v0.3.4`
version number is permanently bound to the old hash and can never be corrected. Any consumer
with a cold module cache — including a new user running `go get github.com/amikos-tech/chroma-go`
— hits this, not just CI. The Windows/macOS split is a cache-warmth artifact, not a platform issue.

</confirmed_root_cause>

<decisions>
## Implementation Decisions

### v0.3.5 base content
- Cut `v0.3.5` in `amikos-tech/chroma-go-local` at **exactly commit `ad3a5aa68f0434670bb8cc39811e69930f40ea70`** —
  the commit `v0.3.4` currently points to.
- Rationale: zero content delta from what consumers already build against. This purely renames
  a burned version number. `main` is 13 commits ahead (dependabot bumps, CI changes); shipping
  those would bundle unrelated changes into a checksum hotfix and widen the validation surface.
- **Do NOT re-tag `v0.3.4` again.** Re-pointing a published tag is what caused this.

### Bump scope in this repo
- Root `go.mod` + `go.sum`, **and** all 9 `examples/v2/*/go.mod` + `go.sum` files that pin
  `chroma-go-local v0.3.4` as an indirect dependency.
- Rationale: the example modules are independent Go modules and will hit the identical failure
  on a cold cache. Affected: `basic`, `array_metadata`, `embedding_function_basic`, `auth`,
  `persistent_client`, `schema`, `metadata_filters`, `search`, `tenant_and_db`.

### Prevention
- **Fix only.** No CI guards, no cold-cache check job, no unrelated hardening in this repo.
- Rationale: the defect is upstream in `chroma-go-local`'s release process, not here. Adding a
  guard to this repo would be scope creep against the actual cause.

### Upstream tag push — AUTHORIZED
- User explicitly authorized pushing an annotated tag `v0.3.5` at `ad3a5aa` to the public
  `amikos-tech/chroma-go-local` repo, having been told this is a one-way door (once
  `sum.golang.org` notarizes it, the version number is frozen permanently).
- Mechanism: annotated tag push (NOT `workflow_dispatch`). A tag push signs as
  `refs/tags/v0.3.5`, matching `localLibraryCosignIdentityTemplate`; `workflow_dispatch`
  would sign as `refs/heads/main`, which the client rejects for anything but v0.3.4.

### Upstream release workflow run
- Let it run; ignore the outcome. No v0.3.5 artifacts are required (see RESEARCH.md Q1).
- The workflow at `ad3a5aa` failed at the `Upload artifacts to R2` step when v0.3.4 was
  tag-pushed (run `23289602361`, exit 255). A red run is cosmetic noise.
- Do NOT cancel mid-run — that risks a partial R2 upload.
- Do NOT repair the upstream workflow; that is out of scope for issue #512.

### Claude's Discretion
- Whether `go mod tidy` or a targeted `go get` is used to regenerate hashes, provided the
  result is a legitimate re-resolution and not a suppression.

### Version constants — DO NOT TOUCH (from RESEARCH.md Q1/Q4)
- `defaultLocalLibraryVersion = "v0.3.4"` (`client_local_library_download.go:29`) — pins the
  native artifact version. Bumping it would make v0.3.5 release artifacts a hard runtime
  requirement. The Go module version and the native artifact version are decoupled by design;
  no parity assertion exists between them.
- `localLibraryCosignMainIdentityVersion = "v0.3.4"` (`:42`) — single-valued back-compat
  allowance for the `refs/heads/main`-signed v0.3.4 bundle. Changing it revokes verification
  of the artifacts every current user pulls.
- `scripts/offline_bundle/main.go:31`, `scripts/fetch_runtime_deps.sh:10` — must stay
  consistent with `defaultLocalLibraryVersion`.
- `docs/docs/client.md:107`, `docs/go-examples/docs/run-chroma/persistent-client.md:100` —
  document the pinned artifact version; editing them would make them wrong.

</decisions>

<constraints>
## Hard Constraints

From the issue, and non-negotiable:

- **Do NOT** delete the `go.sum` line to make the error disappear.
- **Do NOT** set `GONOSUMDB` / `GONOSUMCHECK` / `GOSUMDB=off` / `GOFLAGS=-mod=mod` in the repo
  or in CI to bypass verification. Those suppress the signal rather than resolve it.
- **Do NOT** re-tag `v0.3.4`.
- The only acceptable resolution is a new version number with correctly notarized content.
- Note: `GOSUMDB=off` was used during diagnosis in an isolated throwaway module under the
  scratchpad directory. It must not appear anywhere in the repository or CI.

</constraints>

<specifics>
## Specific Ideas

- `chroma-go-local` is a **direct, production** dependency here — imported by
  `pkg/api/v2/client_local.go` and `pkg/api/v2/client_local_embedded.go`, not test-only.
- `pkg/api/v2/client_local_library_download.go` downloads platform-native libraries from
  `https://releases.amikos.tech/chroma-go-local/<version>/` and verifies them with cosign
  against identity
  `https://github.com/amikos-tech/chroma-go-local/.github/workflows/release.yml@refs/tags/<tag>`.
  **Open question for research:** does bumping the Go module version to `v0.3.5` also require
  published release assets (archives, `SHA256SUMS`, cosign bundles) at that version? If the
  downloaded library version is derived from the module version, the upstream release must
  publish artifacts, not just move a Git tag.
- `pkg/api/v2/client_local_crosslang_integration_test.go:146` carries a comment
  "chroma-go-local v0.3.4 supports Chroma 1.5.5" that may need updating.
- `scripts/offline_bundle/main_test.go:339` references a `v0.3.4` SHA256SUMS URL.

</specifics>
